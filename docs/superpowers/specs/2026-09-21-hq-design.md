# hq — an Elixir message bus for Claude Code sessions

**Status:** design, awaiting implementation
**Date:** 2026-09-21
**Replaces:** `~/.local/bin/bdherd` (preserved at `reference/bdherd.bash`)

## 1. Why

`bdherd` was a 492-line bash script that dispatched beads-ready tasks to Claude
agents in Herdr worktrees. It worked, but it got the model wrong in one decisive
way: **agents could not interact with each other.** Its only handoff was a
`RESULT:` line grepped out of a pane *after* an agent had already finished. A
task that needed something from a peer mid-flight had no way to ask.

It had three further structural problems:

- **Wave-based.** An entire wave had to finish before the next was dispatched, so
  the slowest agent set the pace for every other.
- **Polling.** `herdr agent wait` blocked a shell per agent. A `blocked` agent
  stalled the whole run until a human noticed.
- **Policy welded to transport.** Beads selection, worktree creation, branch
  merging and message delivery were one script, so none of them could change
  independently.

`hq` keeps the mechanics `bdherd` got right, discards the wave scheduler, and
makes peer-to-peer messaging the primitive everything else is built from.

## 2. Shape

Elixir is **transport, supervision and spawn mechanics only.** It holds no beads
logic, no scheduler and no merge strategy. All policy lives in an orchestrating
Claude session that the user starts by hand.

```
   user ──starts──▶ orchestrator (Claude, in a Herdr pane)
                         │  reads the epic from beads itself (br)
                         │  decides who to spawn, when, and what to merge
                         │
                         ▼  hq spawn / hq send
               ┌────────────────────────┐
               │   hq daemon (Elixir)   │◀──── hq send ──── worker-a
               │   routes + supervises  │◀──── hq send ──── worker-b
               └───────────┬────────────┘        peers address each other
                           │                     directly; the orchestrator
                           ▼ types into I/O      is not a required hop
                   worker-a, worker-b, …
```

The division is the point. When the dispatch policy is wrong, it is fixed by
re-prompting an agent, not by editing Elixir.

### Why Elixir specifically

Not for novelty. The mapping is unusually direct:

- Herdr pushes **one event stream per pane** (§3). One GenServer per agent, each
  owning its own event socket, makes the actor boundary and the connection
  boundary the same boundary. A dropped socket takes down exactly one Session,
  which its supervisor restarts and re-syncs.
- A queued message waiting for an agent to go idle **is** a process mailbox.
- Agents are external OS processes owned by Herdr. The BEAM's "let it crash"
  posture is safe here precisely because crashing `hq` cannot kill an agent
  (§10) — the supervision tree recovers state from Herdr rather than owning it.

## 3. Verified protocol facts

These were probed against the live Herdr server (0.9.1, protocol 22) rather than
assumed. Two of them constrain the implementation directly.

| Fact | Evidence | Consequence |
|---|---|---|
| NDJSON over `~/.config/herdr/herdr.sock`; `id` must be a **string** | integer `id` → `invalid_request` | trivial from Elixir with `packet: :line` |
| **One request per connection.** A second request on the same socket is never answered | 3 pings sent at once → 1 reply | every call is a fresh connect; negligible on a unix socket |
| `events.subscribe` holds the connection open and thereafter serves **only** events | `agent.list` after subscribing → no reply | subscriptions need dedicated connections |
| Events genuinely arrive, promptly | created+closed a scratch pane; both events pushed within ~2s | no polling anywhere in the design |
| `pane.agent_status_changed` and `pane.output_matched` require a `pane_id` | `missing field pane_id` | **one event connection per agent** |
| `pane.created/closed/exited/agent_detected` are global | subscribe succeeds with no pane_id | one extra connection for the roster |
| `HERDR_PANE_ID` is only set inside Herdr-managed panes | unset in a non-Herdr shell | `hq register` must fail with a clear message outside Herdr |
| **The pushed `event` kind's casing is NOT consistently snake_case — it varies per event type, so it cannot be assumed from the (always-dotted) subscription type.** | Subscribing `pane.agent_status_changed` and forcing a transition returns `"event":"pane.agent_status_changed"` (dotted, unchanged); `pane.closed` returns `"event":"pane_closed"` (snake_case); `pane.exited` not observed | `Hq.Herdr.Events` normalizes the pushed kind (`.` → `_`) once, at the boundary, before forwarding `{:hq_event, kind, data}` to its owner — every consumer matches one canonical snake_case spelling regardless of which form Herdr used |

Agent status is one of `idle`, `working`, `blocked`, `done`, `unknown`. Names
must match `[a-z][a-z0-9_-]{0,31}` and be unique among live agents.

## 4. Process tree

```
Hq.Application
├── Hq.Roster            global event connection
│                        (pane.agent_detected, pane.exited, pane.closed)
│                        reaps dead sessions; does NOT auto-adopt (§5)
├── Registry             name → pid, :unique
├── Hq.SessionSup        DynamicSupervisor, restart: :transient
│   ├── Hq.Session "orchestrator"   pane w1:p1 · status · mailbox · own event conn
│   ├── Hq.Session "worker-a"       pane w5:p1 · …
│   └── Hq.Session "worker-b"       …
└── Hq.Control           listener on ~/.hq/control.sock, one process per CLI call
```

`Hq.Herdr` is a stateless module, not a process: `call(method, params)` opens a
connection, writes one line, reads one line, closes. This is not a workaround —
it is what the server's protocol requires.

`Hq.Session` never blocks on a Herdr call. Delivery runs in a supervised Task so
a slow `agent.prompt` cannot stall the mailbox that is meant to be receiving
messages.

## 5. Identity and adoption

An `hq` name **is** the Herdr agent name. There is no mapping table, so
`herdr agent list` and `hq ls` can never disagree.

`hq` supervises only sessions it spawned or that explicitly registered. It does
**not** auto-adopt every Claude session it can see. This is deliberate: adoption
makes a session addressable, and typing a peer's message into a session the user
is working in interactively would be intrusive and surprising. The Roster still
watches global events so it can reap sessions that die.

`hq register <name>` reads `$HERDR_PANE_ID`, renames that pane's agent via
`agent.rename`, and starts a Session. Outside Herdr it fails with a message
saying so, rather than guessing at a pane.

## 6. Delivery

The core loop. No timers, no polling, no blocking primitives.

```
worker-a: hq send worker-b "schema frozen: users.id is uuid"
            │
            ▼
   Session[worker-b].mailbox ← enqueue        (worker-b is `working`)
            │
            │  … worker-b finishes its turn …
            ▼
   pane.agent_status_changed → {idle}          (pushed, ~instant)
            │
            ▼
   agent.prompt worker-b:
     ┌──────────────────────────────────┐
     │ [hq] message from worker-a:      │   ← typed into its I/O, fully visible
     │ schema frozen: users.id is uuid  │
     └──────────────────────────────────┘
            │
            ▼
   worker-b starts a turn on it
```

Because delivery types into an **idle** session, the message *is* the wakeup.
Agent works → idles → mail lands → works again. That is the entire loop, and it
is driven wholly by pushed events.

**Rules:**

- Deliver on `idle` and `done`. Hold on `working`, `blocked` and `unknown`.
  `unknown` means Herdr could not classify the pane; it is not proof of
  readiness, so it must not be treated as one.
- Per-mailbox FIFO.
- **Coalesce.** A flush of N queued messages produces one `agent.prompt`, not N.
  Otherwise a burst of three messages fires three separate turns and the agent
  thrashes.
- **Settle before delivering.** Status can flap. After observing `idle`, wait
  ~400ms and re-read status before writing. `agent.prompt` also rejects a
  blocked agent server-side, which is the backstop.
- Use `agent.prompt`, never `pane.send_text`: it honours the pane's live
  bracketed-paste mode and sends text plus Enter as one ordered submission.
  Do **not** pass `--wait` — the Session tracks state through events instead.

### Message envelope

Delivered text is prefixed so the receiving agent can always tell peer mail from
its own operator's instructions:

```
[hq] message from worker-a:
<body>
```

and for a coalesced flush:

```
[hq] 3 messages

from worker-a:
<body>

from worker-b:
<body>
```

## 7. CLI surface

An escript. ~300ms BEAM start is immaterial against an agent turn.

```
hq register <name>          name the calling pane; start supervising it
hq spawn <name> [--worktree] [--cwd PATH] [--kind claude]
                [--task "..."] [--permissive]
hq send <name> "<msg>"      queue until the target is idle
hq ls                       names, status, cwd, mailbox depth
hq inbox                    what is queued for the calling pane ($HERDR_PANE_ID)
hq release <name>           stop supervising (does not kill the agent)
hq daemon                   run the supervision tree in the foreground
```

### Daemon autostart

The user never starts the daemon. The CLI connects to `~/.hq/control.sock`; on
`ENOENT`/`ECONNREFUSED` it starts `hq daemon` detached, waits for the socket,
and retries. Several agents can call `hq` simultaneously, so startup is guarded
by an `O_EXCL` lockfile — without it, a burst of concurrent `hq send` calls
would race to spawn competing daemons.

### Control protocol

NDJSON over `~/.hq/control.sock`, one request per connection, mirroring Herdr's
own shape for consistency.

## 8. Spawn sequence

Ported from `bdherd`, which had this sequence right (see
`reference/bdherd.bash` lines 176-226):

1. `worktree.create` with `--base` and a local-only branch — or `pane.split`
   when `--worktree` is absent.
2. Run `tools/worktree-env.sh <path>` if present. The thri5 monorepo derives
   per-checkout compose ports from the directory name; skipping this collides
   the new checkout's app ports with every other checkout's.
3. `pane.run 'unset ANTHROPIC_API_KEY CLAUDE_CODE_OAUTH_TOKEN'`. Stale exports
   in the shell profile make Claude Code open a credential dialog and sit there
   blocked forever. This one line is why `bdherd` worked at all.
4. `agent.start <name> --kind claude` (plus `--dangerously-skip-permissions`
   when `--permissive`).
5. Deliver the protocol preamble (§9) and `--task` as the first message.

## 9. Agent onboarding

Nothing in a fresh Claude session knows `hq` exists. `bdherd` solved this by
baking instructions into every prompt it typed; `hq` replaces that with two
mechanisms.

**The skill** lives at `skills/hq/SKILL.md` **inside this repo**, symlinked to
`~/.claude/skills/hq` by `install.sh`. Keeping it in-repo means it is versioned
alongside the CLI verbs it documents, and editing it here updates the live skill
with no copy step. It teaches the orchestrator to register itself, read the epic
from beads, spawn workers and route messages.

**The preamble** is prepended by `hq spawn` to every worker's first message: a
short block stating the worker's name, that `hq send <peer> "..."` reaches
peers, that `hq ls` shows who is alive, and that mail arrives prefixed `[hq]`.
Workers therefore need no configuration of their own.

## 10. Failure handling

Several cases below "notify the orchestrator". Concretely: a Session records the
name that spawned it (`spawned_by`), and notices are delivered to that session
as ordinary `[hq]` mail. A session with no live parent — a hand-registered one,
or one whose parent has exited — logs to `~/.hq/hq.log` instead. There is no
special orchestrator identity; it is a participant like any other.

- **Herdr socket drops.** Sessions are independent processes and keep their
  mailboxes. Each reconnects with exponential backoff and re-syncs status via
  `agent.get`. The Roster does the same.
- **Target `blocked`** (approval or question dialog). Hold the mailbox and
  notify the orchestrator: `worker-b blocked, 2 held`. `hq` never answers a
  dialog — a worker asking to do something unexpected is a human decision.
- **hq daemon dies.** Agents belong to Herdr and are untouched. On restart the
  Roster re-adopts previously supervised sessions from `agent.list` and replays
  persisted mailboxes (§11).
- **Unknown target.** `hq send` fails immediately and prints the live roster,
  rather than silently queueing for a name that will never exist.
- **Agent exits with mail pending.** Undelivered messages are reported to the
  orchestrator so the work they represent is not lost silently.
- **Name collision.** `hq spawn` with a live name fails; Herdr requires
  uniqueness among live agents and `hq` surfaces that rather than working around
  it.

## 11. Persistence

Mailboxes are written to `~/.hq/mailbox/<name>.ndjson` on enqueue and rewritten
on delivery. Volume is tiny and it removes a silent-loss failure mode: a daemon
restart would otherwise eat every queued message with no trace.

Supervised session names persist to `~/.hq/sessions.json` so a restart knows
which agents to re-adopt (§5 — it must not adopt everything it sees).

Logs go to `~/.hq/hq.log`.

## 12. Testing

The system talks to an external server, so the fake is the centre of the
strategy: **`test/support/fake_herdr.ex` is a real unix-socket listener** that
speaks the same NDJSON, enforces one-request-per-connection, and can push events
on subscription connections. Tests point `:hq, :herdr_socket` at a temp path.
This gives genuine end-to-end coverage with no Herdr running.

TDD throughout. Coverage that matters:

- one-request-per-connection is honoured (a client that reuses a socket hangs)
- a message is **never** typed while the target is `working`, `blocked` or
  `unknown`
- FIFO order; N queued messages produce exactly one `agent.prompt`
- status flap does not cause a double delivery
- `blocked` holds mail and notifies the orchestrator
- socket drop → reconnect → re-sync, mailbox intact
- daemon restart replays persisted mailboxes
- concurrent `hq` invocations start exactly one daemon
- control-socket round-trips for every CLI verb

Plus one scripted manual smoke test against real Herdr, since the fake encodes
assumptions about a server that can change under it.

## 13. Out of scope for v1

Deliberately excluded, each because it is policy that belongs in the
orchestrator or complexity with no current demand:

- Beads integration in Elixir — the orchestrator uses `br` itself.
- Branch merging and conflict handling.
- Any wave scheduler or dependency graph walking.
- Blocking `hq ask` with reply correlation — a reply is just another message,
  and an idle agent is woken by one.
- Web UI. `hq ls` plus Herdr's TUI is the view.
- Multi-machine (`--machine`) support.

## 14. Setup

One-time, performed by `install.sh`:

1. `brew install elixir` (1.20.4 bottled; pulls Erlang/OTP). Nothing is
   installed today.
2. `mix escript.build`, link the escript onto `PATH`.
3. Symlink `skills/hq` → `~/.claude/skills/hq`.
4. Add the worker allowlist (§15) to Claude settings.

Requires a running Herdr server; it does not autostart, and `hq` reports that
clearly rather than hanging.

## 15. Permissions

Allowlist by default, fully permissive on an explicit toggle.

Default worker settings pre-grant `Bash(hq:*)` plus git, test and read-only
tooling. Peer messaging therefore never trips an approval dialog — a worker
stalling on permission to send a message would defeat the entire mechanism —
while a genuinely unexpected command still stops and is surfaced as `blocked`.

`hq spawn --permissive` starts the worker with permissions skipped entirely, for
runs where nothing should ever stall. The worktree limits the blast radius but
does not eliminate it, so this is opt-in per spawn.

## 16. Migration from bdherd

- `bdherd` is preserved at `reference/bdherd.bash` for the spawn sequence in §8.
- `~/.local/bin/bdherd` is deleted once `hq spawn` works.
- Seven agents and their worktrees are live from earlier `bdherd` runs. They are
  listed for the user to clean up by hand; `hq` deletes nothing it did not
  create.

## 17. Open question

`bdherd` merged dependency branches into a worker's worktree before starting it,
so a task built on its dependencies' work rather than a stale base. v1 drops
merging entirely, which means the orchestrator must either serialise work that
shares files or merge branches itself. This is acceptable for a first version
but is the most likely source of a follow-up.
